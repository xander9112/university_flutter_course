## Обзор папок в Flutter приложении

.dart_tool - директория используется пакетным менеджером языка программирования Dart (который называется Pub), а также другими инструментами языка программирования Dart. В данную папку мы не вносим никаких изменений.

android - содержит специфические для платформы Android настройки, исходный код и ресурсы. Здесь находятся редактируемые файлы AnroidManifest.xml и build.gradle, а также ресурсная папка res (в которой, например, будет находиться иконка приложения для Android в различных разрешениях). Если же у вас появится необходимость добавить специфичный для Android платформы код, то вы будите вносить изменения именно сюда.

build - в только что созданном проекте данной директории нет, она автоматически создается при запуске проекта. В ней находятся различные продукты сборки и запуска приложения, а также, после запуска команды flutter build appbundle, будут находиться apk и aab файлы необходимые для релиза.

ios - данная папка очень похожа на папку android, с тем отличием, что в ней находятся специфичные для платформы iOS файлы: настройки, исходный код и ресурсы. Здесь имеется папка Assets.xcassets, которая очень похожа на res в андроиде, а также файл Info.plist, похожий на AndroidManifest.xml. Если же у вас появится необходимость добавить специфичный для iOS платформы код, то вы будите вносить изменения именно сюда.

lib - именно в этой директории проводится основная работа по написанию кода. Изначально внутри находится только файлик main.dart, который содержит функцию main - точку входа в наше приложение. В процессе разработки внутри данной директория появляется целая иерархия других папок, например, папка models - с файлами моделей (описанием данных, которые используются в приложении), или директория screens - с экранами приложения, или же директория services (прослойка для работы с различными API и подключенными пакетами). 

test - в данную папку будет добавлять код связанный с автоматическим тестированием.

.gitignore - файл, содержащий список файлов, папок и расширений, которые ледует игнорировать в проекте при работе с Git.

.metadata - содержит связанные с проектом метаданные. Никаких изменений в этот файл самостоятельно вносить не нужно.

analysis_options - файл с опциями для статического анализа кода.

название_проекта .iml - файл автоматически называется по имени вашего Flutter проекта и содержит дополнительные настройки. Никаких изменений в этот файл вносить не нужно.

pubspec.lock - автоматически генерируемый файл, основанный на файле .yaml (смотрите ниже). Он содержит подробную информацию обо всех зависимостях. Никаких изменений в файл, самостоятельно, вносить не нужно.

pubspec.yaml - это конфигурационный файл проекта. Здесь объявляются зависимости, которые необходимы проекту, подключаются необходимые шрифты и подключаются ассеты (картинки, иконки, аудио файлы и т.д.). В данном файле можно изменить название, описание, а также версию кода приложения.

README.md - markdown файл, который используется для описания проекта. В него можно добавлять то, для чего нужен проект, как его настраивать и как им пользоваться.

Структура pubspec.yaml (инфа на англ https://dart.dev/tools/pub/pubspec )

Каждому пакету pub нужны некоторые метаданные, чтобы он мог указать свои зависимости. Пакеты Pub, которыми делятся с другими, также должны предоставлять некоторую другую информацию, чтобы пользователи могли их обнаружить. Все эти метаданные входят в pubspec пакета: файл с именем pubspec.yaml, написанный на языке YAML.

В pubspec могут быть следующие поля:

name

Каждому пакету нужно имя. Это то, как другие пакеты ссылаются на ваш, и как он выглядит в мире, если вы его опубликуете. Имя должно быть написано строчными буквами, с подчеркиванием для разделения слов, just_like_this. Используйте только основные латинские буквы и арабские цифры: [a-z0-9_]. Кроме того, убедитесь, что имя является допустимым идентификатором Dart — оно не начинается с цифр и не является зарезервированным словом. Постарайтесь выбрать понятное, лаконичное и еще не используемое имя. Рекомендуется выполнить быстрый поиск пакетов на сайте pub.dev, чтобы убедиться, что ничто другое не использует ваше имя.

version

У каждого пакета есть версия. Номер версии требуется для размещения вашего пакета на сайте pub.dev, но его можно не указывать для пакетов, предназначенных только для локального использования. Если вы опустите его, ваш пакет неявно имеет версию 0.0.0. Управление версиями необходимо для повторного использования кода, позволяя ему быстро развиваться. Номер версии — это три числа, разделенные точками, например 0.2.43. Он также может иметь суффикс сборки (+1, +2, +hotfix.oopsie) или предварительной версии (-dev.4, -alpha.12, -beta.7, -rc.5). Каждый раз, когда вы публикуете свой пакет, вы публикуете его в определенной версии. Как только это будет сделано, эта версия больше недоступна для изменений. Чтобы внести дополнительные изменения, вам понадобится новая версия.

description

Это необязательно для ваших личных пакетов, но если вы собираетесь опубликовать свой пакет, вы должны предоставить описание, которое должно быть на английском языке. Описание должно быть относительно коротким — от 60 до 180 символов — и сообщать случайному читателю то, что он может захотеть узнать о вашем пакете. Воспринимайте описание как рекламный ход вашего пакета. Пользователи видят это, когда просматривают пакеты. Описание представляет собой обычный текст.

homepage

Optional. Это должен быть URL-адрес, указывающий на веб-сайт вашего пакета. Для размещенных пакетов этот URL связан со страницей пакета. Хотя указывать домашнюю страницу необязательно, укажите ее или репозиторий (или и то, и другое). Это помогает пользователям понять, откуда пришел ваш пакет. 

repository

Необязательное поле репозитория должно содержать URL-адрес репозитория исходного кода вашего пакета, например, https://github.com/<user>/<repository>. Если вы публикуете свой пакет на сайте pub.dev, на странице вашего пакета отображается URL-адрес репозитория. Хотя предоставление репозитория не является обязательным, укажите его или домашнюю страницу (или и то, и другое). Это помогает пользователям понять, откуда пришел ваш пакет. 

issue_tracker

Необязательное поле issue_tracker должно содержать URL-адрес системы отслеживания проблем пакета, где можно просмотреть существующие ошибки и зарегистрировать новые ошибки. Сайт pub.dev пытается отобразить ссылку на систему отслеживания проблем каждого пакета, используя значение этого поля. Если issue_tracker отсутствует, но репозиторий присутствует и указывает на GitHub, то сайт pub.dev использует трекер по умолчанию (https://github.com/<user>/<repository>/issues).

documentation

У некоторых пакетов есть сайт, на котором размещена документация, отдельно от главной домашней страницы и справочника по API, созданного Pub. Если у вашего пакета есть дополнительная документация, добавьте документацию: поле с этим URL-адресом; pub показывает ссылку на эту документацию на странице вашего пакета

dependencies

Зависимости — это смысл существования pubspec. В этом разделе вы перечисляете каждый пакет, который необходим вашему пакету для работы. Зависимости делятся на два типа. Обычные зависимости перечислены в разделе dependencies: это пакеты, которые также понадобятся всем, кто использует ваш пакет. Зависимости, которые необходимы только на этапе разработки самого пакета, перечислены в разделе dev_dependencies. В процессе разработки вам может понадобиться временно переопределить зависимость. Вы можете сделать это, используя dependency_overrides.

dev_dependencies

Can be omitted if your package has no dev dependencies. Learn more.

dependency_overrides

Can be omitted if you do not need to override any dependencies. Learn more.

environment

Пакет может указать, какие версии своих зависимостей он поддерживает, но у пакетов есть еще одна неявная зависимость: сама платформа Dart. Платформа Dart со временем развивается, и пакет может работать только с определенными версиями платформы. Пакет может указать эти версии с помощью ограничения SDK. Это ограничение входит в отдельное поле среды верхнего уровня в pubspec и использует тот же синтаксис ограничения версии, что и зависимости.

executables

Пакет может предоставлять один или несколько своих сценариев в виде исполняемых файлов, которые можно запускать непосредственно из командной строки. Чтобы сделать сценарий общедоступным, укажите его в поле исполняемых файлов. Записи перечислены в виде пар ключ/значение: <имя исполняемого файла>: <Dart-script-from-bin>

platforms

Когда вы публикуете пакет, pub.dev автоматически определяет платформы, которые поддерживает пакет. Если этот список поддержки платформ неверен, используйте платформы, чтобы явно объявить, какие платформы поддерживает ваш пакет. 

Пример: 

publish_to

По умолчанию используется сайт pub.dev. Укажите none, чтобы предотвратить публикацию пакета. Этот параметр можно использовать для указания пользовательского сервера пакетов pub для публикации.

funding

Авторы пакетов могут использовать свойство финансирования, чтобы указать список URL-адресов, предоставляющих информацию о том, как пользователи могут помочь финансировать разработку пакета. Например:

false_secrets

Optional. 

Укажите файлы, которые следует игнорировать при проведении поиска потенциальных утечек секретов.

screenshots

Пакеты могут демонстрировать свои виджеты или другие визуальные элементы с помощью скриншотов, отображаемых на их странице pub.dev. Чтобы указать снимки экрана для отображения пакета, используйте поле снимков экрана. Пакет может содержать до 10 снимков экрана под полем снимков экрана. Не включайте в этот раздел логотипы или другие фирменные изображения. Каждый снимок экрана включает одно описание и один путь. Допускаются как статические, так и анимированные изображения. Файлы скриншотов должны быть небольшими. Каждая загрузка пакета включает в себя все файлы снимков экрана. topics

Авторы пакетов могут использовать поле тем для категоризации своего пакета. Темы можно использовать для облегчения обнаружения во время поиска с помощью фильтров на pub.dev. Pub.dev отображает темы на странице пакета, а также в результатах поиска.

 Функция горячей перезагрузки Flutter помогает быстро и легко экспериментировать, создавать пользовательские интерфейсы, добавлять функции и исправлять ошибки. Горячая перезагрузка работает путем внедрения обновленных файлов исходного кода в работающую виртуальную машину Dart (VM). После того, как виртуальная машина обновляет классы новыми версиями полей и функций, платформа Flutter автоматически перестраивает дерево виджетов, позволяя вам быстро просмотреть результаты ваших изменений.

Запустите приложение из поддерживаемого редактора Flutter или из окна терминала. Целью может быть как физическое, так и виртуальное устройство. Только приложения Flutter в режиме отладки могут быть перезагружены или перезапущены в горячем режиме. Измените один из файлов Dart в вашем проекте. Если вы работаете в IDE/редакторе, который поддерживает инструменты IDE Flutter, выберите «Сохранить все» (cmd-s/ctrl-s) или нажмите кнопку горячей перезагрузки на панели инструментов. Если вы запускаете приложение из командной строки с помощью флаттера, введите r в окне терминала.

Не все изменения в коде можно применить с помощью Hot Reload. Примеры таких кейсов можно найти на этой странице https://docs.flutter.dev/tools/hot-reload#special-cases

В таких случаях необходимо применять Hot Restart, с помощью которого можно полностью перезапустить приложения без его сборки.
