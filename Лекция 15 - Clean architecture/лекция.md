# Лекция 15 - Clean architecture

## Структура приложения

Чистая архитектура - это концепция построения архитектуры систем, предложенная Робертом Мартином (также известного как "дядюшка Боб"). Концепция предполагает построение приложения в виде набора независимых слоёв, что облегчает тестирование, уменьшает связность и делает приложение более простым для понимания.

Основные принципы:

Независимость от фреймворка. Архитектура не зависит от существования какой-либо библиотеки. 

Независимость от UI. Пользовательский интерфейс можно легко изменить, не изменяя остальную систему. Например, веб-интерфейс может быть заменен на консольный, без изменения бизнес-правил.

Независимость от источников данных. Вы можете легко поменять источники данных, такие как базы данных, REST или GraphQL сервисы. Ваши бизнес-правила не связаны с этими источниками данных.

Тестируемость. Бизнес логика может быть протестирована без пользовательского интерфейса, базы данных, сервера или любого другого внешнего компонента.

В чистой архитектуре можно выделить три основных слоя:

Presentation слой. Отвечает за создания UI и логики его работы.

Domain. Реализует бизнес правила нашего приложения.

Data. Отвечает за реализацию доступа к данным.

Важным элементом чистой архитектуры являются принципы SOLID. 

S – Single Responsibility (Принцип единственной ответственности) Каждый класс должен отвечать только за одну операцию. Если класс отвечает за несколько операций сразу, вероятность возникновения багов возрастает – внося изменения, касающиеся одной из операций вы, сами того не подозревая, можете затронуть и другие.

O — Open-Closed (Принцип открытости-закрытости) Классы должны  быть  открыты для расширения, но закрыты для модификации.Когда вы меняете текущее поведение класса, эти изменения сказываются на всех системах, работающих с данным классом. Если хотите, чтобы класс выполнял больше операций, то идеальный вариант – не заменять старые на новые, а добавлять новые к уже существующим.

L — Liskov Substitution (Принцип подстановки Барбары Лисков)

Принцип служит для того, чтобы обеспечить постоянство: класс-родитель и класс-потомок могут использоваться одинаковым образом без нарушения работы программы.

I — Interface Segregation (Принцип разделения интерфейсов)

Принцип служит для того, чтобы раздробить единый набор действий на ряд наборов поменьше – таким образом, каждый класс делает то, что от него действительно требуется, и ничего больше.

D — Dependency Inversion (Принцип инверсии зависимостей)

Этот принцип служит для того, чтобы устранить зависимость классов верхнего уровня от классов нижнего уровня за счёт введения интерфейсов.

Этот принцип особенно актуален в кроссплатформенной разработки, так как сама операционная система платформы является инструментом для бизнес логики нашего приложения, но бизнес логика не должна зависеть от платформы.

Эти принципы способствуют созданию такой системы, которую будет легко поддерживать и расширять в течении долгого времени.

Давайте рассмотрим каждый слой приложения на примере приложения счетчика, который при каждом изменении будет записываться в БД.

Создадим новое приложение с помощью команды

flutter create clean_arch_example

Создадим 3 каталога data, domain, presentation в libs, в котором будет хранить файлы относящиеся к слоям приложения.

## Domain

Для начала создадим наш нашу бизнес логику. 

 Начнем с определения UseCases.

Use case – элемент слоя domain, отвечающий за детализацию, описание действия, которое может совершить пользователь системы;

В нашем случае у нас будет два use case:

Получение счетчика из базы данных, когда пользователь открывается приложение.

Увеличение счетчика на 1.

UseCases должны уметь возвращать результат операции, либо ошибку.

Для удобства передачи и обработки ошибок будет использовать класс Either из пакета dartz, поэтому подключим его

flutter pub add dartz

Класс Either<L, R> это класс содержащие в себе один из двух типов объектов, для простоты называемые Left и Right.

 В левой части мы будем хранить  Failure,  в правой результат операции.

Создадим базовый класс для Failure

```dart
class Failure {
  final int code;
  final String message;
  Failure({required this.code, this.message = ''});
}
```

Далее создадим два абстрактных класса UseCase и  UseCaseNoParams.

```dart
abstract class UseCase<Type, Params> {
  Future<Either<Failure, Type>> call(Params params);
}
abstract class UseCaseNoParams<Type> {
  Future<Either<Failure, Type>> call();
}
```

Так как с большинством источников данных происходит работа через асинхронные методы, то возвращаемое значение UseCase Future<Either<Failure, Type>> является  Future, которое должно вернуть нам либо ошибку в левой части  Either,  либо результат операции в правой.

Теперь мы можем создать два необходимых нам UseCase.

Создадим в каталоге  domain  каталог  usecases и создадим там файл

get_counter_usecase.dart

```dart
class GetCounterUseCase extends UseCaseNoParams<int> {
  @override
  Future<Either<Failure, int>> call() {
    // TODO: implement call
    throw UnimplementedError();
  }
}
```

 и increment_counter_usecase.dart

```dart
class IncrementCounterUseCase extends UseCaseNoParams<int> {
  @override
  Future<Either<Failure, int>> call() {
    // TODO: implement call
    throw UnimplementedError();
  }
}
```

Чтобы получить доступ к данным нам необходим репозиторий, для этого создадим абстрактный класс, который определит интерфейс нашего репозитория.

```dart
abstract class CounterRepository {
  Future<Either<Failure, int>> getCounter();
  Future<Either<Failure, int>> setCounter(int newValue);
}
```

Теперь мы можем дописать наши use кейсы.

Добавим репозиторий как внешнюю зависимость и допишем необходимую логику наших use кейсов.

```dart
class GetCounterUseCase extends UseCaseNoParams<int> {
  final CounterRepository _counterRepository;
  GetCounterUseCase(this._counterRepository);
  @override
  Future<Either<Failure, int>> call() {
    return _counterRepository.getCounter();
  }
}
class IncrementCounterUseCase extends UseCaseNoParams<int> {
  final CounterRepository _counterRepository;
  IncrementCounterUseCase(this._counterRepository);
  @override
  Future<Either<Failure, int>> call() async {
    final result = await _counterRepository.getCounter();
    return result.fold((failure) => Left(failure),
        (currentValue) => _counterRepository.setCounter(++currentValue));
  }
}
```

 В IncrementCounterUseCase мы получаем Either<Failure, int> содержащие текущее значение или ошибку, и с помощью метода  fold указываем что сделать для левой или правой части. Если нам приходит ошибка, мы ее просто отдаем в качестве результата, если приходит текущее значение то вызываем метод репозитория  setCounter в котором передаем новое значение, увеличенное на 1 и уже его результат возвращаем в качестве результата  UseCase.

На этом мы закончили описание нашего слоя бизнес логики для счетчика.

## Data

Слой, в котором описывается работа с источниками данных (сетевой запрос, база данных).

Для того чтобы абстрагировать наш репозиторий от конкретного источника данных создадим абстрактный класс источника данных.

Создадим каталог data/datasource и добавим туда файл counter_local_datasource.dart

```dart
abstract class CounterLocalDatasource {
  Future<Either<Failure, int>> getCounter();
  Future<Either<Failure, int>> setCounter(int newValue);
}
```

Рядом создадим реализацию этого класса, который будет читать и  сохранять данные в обычном файле.

```dart
class FileCounterLocalDatasource implements CounterLocalDatasource {
  @override
  Future<Either<Failure, int>> getCounter() async {
    try {
      final counter = await readData();
      return Right(counter);
    } catch (e) {
      return Left(Failure(code: 1, message: e.toString()));
    }
  }
  @override
  Future<Either<Failure, int>> setCounter(int newValue) async {
    try {
      await writeData(newValue);
      final counter = await readData();
      return Right(counter);
    } catch (e) {
      return Left(Failure(code: 1, message: e.toString()));
    }
  }
  Future<String> get _localPath async {
    final directory = await getApplicationDocumentsDirectory();
    return directory.path;
  }
  Future<File> get _localFile async {
    final path = await _localPath;
    return File('$path/counter.txt');
  }
  Future<void> writeData(int data) async {
    final file = await _localFile;
    // Write the file
    await file.writeAsString(data.toString());
  }
  Future<int> readData() async {
    final file = await _localFile;
    if (!file.existsSync()) {
      file.writeAsStringSync('0');
    }
    // Read the file
    final contents = int.tryParse(await file.readAsString());
    return contents ?? 0;
  }
}
```

Далее мы должны реализовать логику репозитория для работы с нашим источником данных.

```dart
class CounterRepositoryImpl implements CounterRepository {
  final CounterLocalDatasource _counterLocalDatasource;
  CounterRepositoryImpl(this._counterLocalDatasource);
  @override
  Future<Either<Failure, int>> getCounter() {
    return _counterLocalDatasource.getCounter();
  }
  @override
  Future<Either<Failure, int>> setCounter(int newValue) {
    return _counterLocalDatasource.setCounter(newValue);
  }
}
```

В нашем случае она довольно простая, но в реальных проектах здесь может быть логика работы с кешем, сетевыми запросами и с другими различными источниками данных.

На этом мы закончили разработку нашего Data слоя.

## Presentation

Presentation слой представления. Здесь мы будем создавать UI, логику его работы и его состояние.

Для управления состоянием воспользуемся пакетом flutter_bloc, поэтому добавим его в зависимости:

flutter pub add flutter_bloc

Создадим Cubit который при помощи ранее созданых use cases будет обрабатывать состояние нашего UI. Создадим каталог presentation/state и добавим туда файл counter_cubit.dart

```dart
class CounterCubit extends Cubit<int> {
  CounterCubit(
    this._getCounterUseCase,
    this._incrementCounterUseCase,
  ) : super(0) {
    _init();
  }
  final GetCounterUseCase _getCounterUseCase;
  final IncrementCounterUseCase _incrementCounterUseCase;
  void _init() async {
    final result = await _getCounterUseCase();
    result.fold((failure) {}, (counter) => emit(counter));
  }
  void increment() async {
    final result = await _incrementCounterUseCase.call();
    result.fold((failure) {}, (counter) => emit(counter));
  }
}
```

У нас теперь все готово для того чтобы создавать виджеты отображающие, но нам необходимо както внедрить наш cubit со всеми его внешними зависимостями в дерево виджетов.

Объекты нужно создавать «снизу вверх»: источник данных → репозиторий → use cases → cubit. Чтобы виджеты не знали об этой цепочке, соберём её в одном месте — такое место называют **точкой сборки зависимостей** (composition root). Это единственное место в приложении, которое знает о конкретных реализациях; все остальные классы получают зависимости через конструктор и работают с абстракциями.

Создадим каталог lib/di и добавим в него файл configure_dependencies.dart

```dart
CounterCubit createCounterCubit() {
  final CounterLocalDatasource datasource = FileCounterLocalDatasource();
  final CounterRepository repository = CounterRepositoryImpl(datasource);
  return CounterCubit(
    GetCounterUseCase(repository),
    IncrementCounterUseCase(repository),
  );
}
```

Функция собирает все зависимости, необходимые для работы кубита, и возвращает готовый экземпляр.

В небольшом приложении такой ручной сборки достаточно. Когда классов становится много, вручную поддерживать эти цепочки неудобно — в Лекции 16 мы передадим эту работу DI-контейнеру GetIt и генератору Injectable.

Теперь добавим страницу для нашего счетчика, создадим каталог presentation/page и добавим в него файл home_page.dart

Мы создали приложение с одним экраном отделив бизнеслогику от UI приложения и логикой доступа к данным. Чтобы продемонстрировать как можно быстро изменять работу приложения давайте заменим логику с сохранением счетчика в файл. Вместо файла будем использовать пакет shared_preferences.

Для этого создадим новый источник данных. 

Добавил пакет  shared_preferences в зависимости

flutter pub add shared_preferences

Добавим файл shared_pref_counter_local_datasource.dart в каталог data/datasource

```dart
class SharedPrefCounterLocalDatasource implements CounterLocalDatasource {
  @override
  Future<Either<Failure, int>> getCounter() async {
    try {
      final prefs = await SharedPreferences.getInstance();
      return Right(prefs.getInt('counter') ?? 0);
    } catch (e) {
      return Left(Failure(code: 1, message: e.toString()));
    }
  }
  @override
  Future<Either<Failure, int>> setCounter(int newValue) async {
    try {
      final prefs = await SharedPreferences.getInstance();
      await prefs.setInt('counter', newValue);
      return Right(prefs.getInt('counter') ?? 0);
    } catch (e) {
      return Left(Failure(code: 1, message: e.toString()));
    }
  }
}
```

Теперь нам нужно изменить точку сборки зависимостей так, чтобы создавалась имплементация с shared_preferences.

В файле di/configure_dependencies.dart изменим строку

```dart
  final CounterLocalDatasource datasource = FileCounterLocalDatasource();
```

на

```dart
  final CounterLocalDatasource datasource = SharedPrefCounterLocalDatasource();
```

И это все. Мы быстро изменили источник данных, но не изменяли ни бизнес логику приложения, ни UI.  

### Автоматический выбор реализации под платформу

Часто нужно не заменить реализацию источника данных навсегда, а выбирать её в зависимости от платформы: например, на вебе хранить счетчик в  shared_preferences (в браузере это localStorage), а на мобильных платформах — в файле. Domain и presentation слои при этом не должны ничего знать о том, что приложение исполняется на вебе или на телефоне — вся эта логика должна остаться в di.

Flutter предоставляет константу kIsWeb из пакета flutter/foundation.dart, которая вычисляется на этапе компиляции и позволяет определить, собрано ли приложение под веб.

Изменим  di/configure_dependencies.dart, чтобы создавать нужную реализацию  CounterLocalDatasource в зависимости от платформы.

```dart
import 'package:flutter/foundation.dart' show kIsWeb;

CounterCubit createCounterCubit() {
  final CounterLocalDatasource datasource = kIsWeb
      ? SharedPrefCounterLocalDatasource()
      : FileCounterLocalDatasource();
  final CounterRepository repository = CounterRepositoryImpl(datasource);
  return CounterCubit(
    GetCounterUseCase(repository),
    IncrementCounterUseCase(repository),
  );
}
```

Больше никаких изменений не требуется —  GetCounterUseCase, IncrementCounterUseCase, CounterCubit и  HomePage продолжают работать с абстракцией CounterRepository и знать не знают о том, какая реализация источника данных используется под капотом. Это и есть основная выгода принципа инверсии зависимостей: код верхних слоев зависит от абстракций, а не от конкретных платформенных API.

Здесь стоит сделать важную оговорку. kIsWeb — константа времени компиляции, поэтому при сборке под веб компилятор через tree-shaking выкидывает недостижимый код. Но FileCounterLocalDatasource использует dart:io (класс  File), а эта библиотека на вебе недоступна в принципе — если в файле с классом останутся любые обращения к dart:io вне метода, который не вызывается, сборка под веб может не пройти вовсе.

Более надежный способ решить эту проблему — conditional imports, которые позволяют подключать разные файлы в зависимости от платформы уже на этапе компиляции, а не просто выбирать между уже скомпилированными классами.

Создадим три файла в  data/datasource:

counter_local_datasource_provider.dart — точка входа, которую будет использовать di:

```dart
export 'counter_local_datasource_io.dart'
    if (dart.library.js_interop) 'counter_local_datasource_web.dart';
```

counter_local_datasource_io.dart — используется на всех платформах, где доступна dart:io:

```dart
CounterLocalDatasource createCounterLocalDatasource() =>
    FileCounterLocalDatasource();
```

counter_local_datasource_web.dart — используется только при сборке под веб:

```dart
CounterLocalDatasource createCounterLocalDatasource() =>
    SharedPrefCounterLocalDatasource();
```

Теперь в  di/configure_dependencies.dart сборка упрощается и полностью избавляется от ветвления и от прямого упоминания конкретных классов датасорсов:

```dart
  final CounterLocalDatasource datasource = createCounterLocalDatasource();
```

При такой схеме компилятор для веб-сборки вообще не увидит файл  counter_local_datasource_io.dart с dart:io, а для мобильной и десктопной сборки — не увидит файл с shared_preferences-специфичным кодом под веб. Выбор реализации происходит полностью на уровне di и импортов, никак не затрагивая domain и presentation.

Такой же прием удобен и для тестов: можно создать третью, тестовую реализацию  CounterLocalDatasource, которая хранит счетчик просто в памяти, и передать её в конструктор  CounterRepositoryImpl в тесте, не трогая ни бизнес логику, ни UI. Подробно тестирование разберём в Лекции 18.
